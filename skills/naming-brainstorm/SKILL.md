# naming-brainstorm

新規サービス・アプリ・プロジェクトの **名称を考える命名パートナー** スキル。

目的は「名前を大量に出すこと」ではなく、サービスの本質・強み・届けたい印象・対象ユーザー・避けたい誤解を整理した上で、**覚えやすく・言いやすく・使いやすい** 候補を提案すること。

> **使い分け**: コード内の関数名・変数名・型名の命名にはこのスキルを使わない。サービス・プロダクトの「顔となる名前」を決めるためのスキル。

---

## 命名候補の基本条件

候補は、原則として以下を優先する。

- 日本語の場合: ひらがな or カタカナで **3文字 or 4文字**
- 英語の場合: **1音節 or 2音節** 程度の短い語
- 日本語ではこう読むが、英語ではこう書く、という **表記の幅** を許容する
- 覚えやすい / 言いやすい / 口頭で伝えやすい
- サービスの強みや思想がにじむ
- 既存サービス・既存商標・不適切なスラングとの衝突リスクが低い

詳細ルール・名前の型は `references/naming-rules.md` を参照。

---

## 基本動作

最初から候補名を大量に出さない。まず **対話モード** として、ユーザーに質問しながら命名条件を整理する。

**質問は1回につき最大3つまで**。多すぎると進行が止まる。ユーザーの回答が不完全でも、合理的な仮定を置いて前に進める。

質問する時は AskUserQuestion を使うか、自然な日本語で 1〜3 問を箇条書きにして聞く（チャット形式の方が自然な状況なら後者でよい）。

---

## 6段階フロー

### ①ヒアリング

**初回応答テンプレート** — ユーザーが「サービス名を考えたい」「ネーミングしたい」と言ったら、まず以下のように返す:

> まず、名前の方向性を決めるために3つだけ教えてください。
>
> 1. どんなサービス・アプリ・プロジェクトですか？
> 2. そのサービスで一番伝えたい強み、または作った目的は何ですか？
> 3. 主な利用者は誰ですか？
>
> 回答をもとに命名方針を整理してから、3〜4文字の日本語名または1〜2音節の英語名を中心に候補を出します。候補ごとに、既存サービス衝突・商標リスク・スラングリスクも簡易チェックします。

**最初に聞く（3問）**:

1. これはどのようなサービス・アプリ・プロジェクトか？
2. 一番伝えたいことは何か？（強み / 作った目的 / ユーザーに与える価値 / 既存サービスとの違い）
3. 主な利用者は誰か？（一般消費者 / 医師・専門職 / 企業 / 学生 / 子ども / 高齢者 / その他）

**必要に応じて次に聞く（最大3問）**:

4. 名前から受けてほしい **印象**（ブランド人格）は何か？
   - 信頼感 / 親しみやすさ / かわいさ / 知的さ / 速さ / 安心感 / 革新性 / 専門性 / 遊び心
5. **避けたい印象** は何か？
   - 軽すぎる / 医療っぽすぎる / ITっぽすぎる / 怪しい / 子どもっぽい / 高圧的 / 難しい / 既視感が強い
6. 想定する **市場** はどこか？
   - 日本国内のみ / 日本中心だが海外も少し意識 / 最初から海外展開も想定

ユーザーが急いでいる時は質問を最小限にし、仮説ベースで候補出しまで進めてよい。

### ②命名方針の整理

ヒアリング結果をもとに、候補を出す前に **短くサマリ** する。これをユーザーと共有して合意を取ってから候補生成に進む。

整理する項目:

- サービスの一言要約
- もっとも伝えるべき価値
- 名前に込めるべき方向性
- 避けるべき方向性
- 日本語名を優先するか、英語名を優先するか、両方並べるか
- 候補生成時の評価軸（7軸のうち特に重視する2〜3つ）

**例**:

> このサービスは、開業候補地の成功可能性を地図・人口動態・競合・医師の専門性から評価するツール。名前では「医療開業の地図を見る」「成功可能性を見通す」「専門家向けだが親しみやすい」という印象を優先する。日本語名を主軸に、海外展開を意識して英語表記も併記できる形を狙う。

### ③大量生成（発散）

`references/naming-rules.md` の **名前の型** を参照し、型をまたいで20〜30個を **広く発散** する。

**名前の型**（バラエティを安定させるために型ごとに出す）:

| 型 | 例 | 性格 |
|----|------|------|
| 機能型 | メドチズ / カルナビ | サービスの機能・対象をそのまま含む |
| 感情型 | あんしん / よりそい | ユーザーが感じる感情を直接表す |
| 造語型 | メドリス / チズカ | 既存単語の合成・音の遊び |
| 比喩型 | コンパス / ルーペ | サービスの本質を別のモノで例える |
| 専門略語型 | ClinMap / MedNav | 業界用語・英単語の略 |

各型から 4〜6 個ずつ出すと多様性が確保できる。

**この段階では候補を絞らない**。発音できないもの・明らかにダメなもの以外は残す。

### ④絞り込み

20〜30個 → **10個** に絞る。

絞る基準:

- 同じ型の中で似通っているものは1つに代表化
- 第一印象で7軸（後述）の半分以上が△以下になりそうなものを落とす
- ユーザーの「避けたい印象」に該当するものを落とす

絞り込んだ10個について、以下を1行ずつ添えて提示:

- 名称
- 表記案（ローマ字 / カタカナ / ひらがな / 英語）
- 読み
- 由来の種
- 名前の型

ここで一度ユーザーに見せて、方向性が大きく外れていないか確認してもよい（任意）。

### ⑤Web衝突確認

`references/check-procedures.md` を読み、絞った 10候補に対して WebSearch で簡易チェックを行う。

**確認する4観点**:

1. **既存サービス衝突**: `"候補名" サービス` / `"候補名" app` / `"候補名" startup` 等
2. **スラング・不適切語**: `"候補名" slang` / `"候補名" meaning` / `"候補名" Korean meaning` 等
3. **ドメイン目安**: `候補名.com` / `候補名.jp` 等
4. **多言語発音**: 主要言語での読み方推定

**重要な原則**（必ず守る）:

- WebSearch で問題が見つからなくても「絶対に安全」「商標上問題ない」とは **言わない**
- 商標については「リスク評価」であり、**法的な商標クリアランスとは別** と明記する
- Urban Dictionary など低信頼ソースは過度に重視しないが、明確に性的・差別的・侮辱的な意味がある場合は候補から外す
- 候補名が既存サービスと **完全一致** する場合は原則避ける
- 近い領域で似た名称がある場合も、混同リスクを説明する
- 一般名詞や短い造語は検索ノイズが多いため、完全な未使用性だけでなく **サービス領域での混同可能性** を重視する

**効率化**: 10候補 × 4観点 = 40クエリは多すぎる。WebSearch を並列発行し、1候補につき 2 クエリ（衝突系・スラング系）程度に束ねる。詳細は `references/check-procedures.md`。

### ⑥最終候補レポート

絞り込み後の候補について、以下のテーブル形式で提示する:

| 候補名 | 表記案 | 読み | 由来 | 強み | 懸念 | 総合評価 |
|--------|--------|------|------|------|------|----------|

その下に以下を続ける:

#### 7軸スコアリング（各候補、5段階）

| 軸 | 内容 |
|----|------|
| ① 覚えやすさ | 一度聞いて翌日も思い出せるか |
| ② 言いやすさ | 口頭で滑らかに発音できるか |
| ③ サービス内容との適合度 | コンセプトとどれだけ合うか |
| ④ 独自性 | 既存サービスからどれだけ離れているか |
| ⑤ 検索しやすさ | Google で見つかりやすいか（ノイズが少ないか）|
| ⑥ 将来展開のしやすさ | ピボット・シリーズ展開に耐えるか |
| ⑦ 不適切語・スラングリスクの低さ | 各国で問題ないか |

#### 攻め案 / 無難案 / 本命案 への振り分け

候補が全部同じ温度感だと選びにくい。10候補を以下に振り分けて意思決定しやすくする:

- **無難案** — 信頼感があり外しにくい
- **親しみ案** — 親近感がありユーザーに刺さりやすい
- **攻め案** — 少し挑戦的だが印象に残る造語
- **本命案（1〜3個）** — 7軸スコアと方針整合性から最も推せる

#### 推薦理由と避けた方がよい候補

- なぜ本命案が強いのか、軸ごとに説明
- 衝突リスク・不適切語リスク・発音しにくさ・意味の弱さがある候補は明示

## ユーザーが候補を1つ選んだ後

候補を1つ選んだら、**採用後の見え方** までまとめる。`references/report-template.md` のフォーマットに沿って以下を作成:

1. **名前の由来ストーリー**（マーケ用に長めに、3〜5行）
2. **1行説明文**
3. **サービス紹介文**（数行）
4. **ロゴ化する場合の方向性**
5. **タグライン候補**（3案ほど）
6. **ドメイン・SNS アカウント向け表記バリエーション**（`name.com` / `name.app` / `@name_jp` など）
7. **商標・既存サービス衝突の再確認ポイント**（次にユーザーが取るべき公式確認手段）

**採用後ビュー（必ず並べる）**:

```text
サービス名:
タグライン:
1行説明:
URL候補:
ロゴにしたときの印象:
想定ユーザーが聞いたときの印象:
```

これがあると、名前単体ではなく **「サービス説明文とセットで強いか」** を判断できる。

**出力先**:
- プロジェクトに `docs/` があれば: `docs/YYYYMMDD_naming_report.md`
- なければ: プロジェクトルートに `naming_report.md`

保存後、ユーザーに保存先パスを伝えて完了。

## 追加ルール（重要）

- **会話は常に日本語**
- ユーザーが急いでいる場合は、質問を最小限にして仮説ベースで候補を出す
- ユーザーが気に入った候補を示した場合は、その方向性に寄せて追加候補を出す
- 候補が弱い場合は、無理に褒めず、率直に改善案を出す
- 響きが良くても、意味が伝わらない場合はその弱点を説明する
- 意味が強くても、言いにくい場合は候補として下げる
- 医療・教育・金融など信頼性が重要な領域では、軽すぎる名前や怪しい響きの名前を避ける
- 子ども向け・一般向け・専門職向けで評価基準を変える
- 最終的には、名前単体ではなく **「サービス説明文とセットで強いか」** を評価する
- **法的判断は断定しない**: 「商標登録可能」「絶対に大丈夫」とは言わず、「簡易検索上の衝突リスク」として評価する
- WebSearch 結果は **目安**。正式な商標判断には専門家（弁理士）による確認が必要、と明記する
