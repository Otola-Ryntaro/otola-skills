# zero-design: ゼロベース再設計分析

プロジェクトをゼロから自由に設計できるとしたらどうするか、という視点で現行設計を分析する。
コード変更は一切行わない。

## 設計原則（このスキルが守ること）

1. **文脈が先、テンプレは後**: ユーザーの困りごとを聞く前に調査を始めない。観点はプロジェクト実態から選ぶ
2. **根拠のない指摘は書かない**: file:line を示せない指摘は本文に載せない。一般論の推奨は付録に隔離する
3. **件数ノルマ禁止**: 指摘0件の観点は「0件」と書く。観点ごとに何か指摘をひねり出さない
4. **反証を通ったものだけ報告**: REJECTED された指摘はレポートから除外する
5. **次工程を勝手に実行しない**: /ticket-gen への接続は提示のみ（ticket-gen 自身の流儀と同じ）

## 実行プロトコル

### Phase 0: Intake（プランモードで開始）

1. `EnterPlanMode` でプランモードに入る（Phase 2 の承認まで維持）
2. `AskUserQuestion` で以下を確認（1〜3問。すでに会話で明らかな項目は聞かない）:
   - **動機**: 何に困っているか（遅い／壊れやすい／変更しにくい／不安がある／全体像を知りたい 等）
   - **優先目標**: 速度・保守性・セキュリティ・スケール・DX から上位1〜2個
   - **不可侵領域**: 触れてはいけない・変更提案不要の領域（あれば）
3. プロジェクト種別を自動検出:
   - マーカー: `package.json` / `pyproject.toml` / `Cargo.toml` / `next.config.*` / `Dockerfile` / モノレポ構成（workspaces, turbo.json）等
   - 種別: Web アプリ / API サーバー / CLI / ライブラリ / モノレポ / ドキュメントリポジトリ
   - テストの有無・規模（ファイル数、概算行数）
4. `date +%Y%m%d` で日付取得。出力先: `docs/YYYYMMDD_zero_design_report.md`

### Phase 1: 軽量偵察（サブエージェント不使用）

メインコンテキストで短時間の兆候スキャンを行い、Phase 2 の観点提案の材料にする:

- ディレクトリ構造マップ（2〜3階層）
- 巨大ファイル（800行超）・巨大ディレクトリの検出
- TODO / FIXME / HACK 密度
- テスト配置と実行コマンドの確認（package.json scripts 等）
- `.claude/error-patterns/` があれば既知パターンを読む（過去に壊れた領域は重点候補）
- CLAUDE.md / README / ARCHITECTURE.md の設計意図

### Phase 2: 観点の動的選択（承認ゲート）

1. Phase 0 の動機・目標 × Phase 1 の兆候から、調査観点を **3〜6個** 提案する
2. 観点候補は [references/lens_catalog.md](references/lens_catalog.md) から選び、必要なら独自観点を追加する
3. **プロジェクト種別に該当しない観点は提案しない**（例: CLI ツールにフロントエンド観点、UI のないライブラリに a11y 観点）
4. 各観点に「なぜこの観点か（動機・兆候との対応）」を1行添えて提示し、**ユーザー承認を得てから** `ExitPlanMode` で深掘りに進む

### Phase 3: 深掘り調査（承認観点のみ並列サブエージェント）

承認された観点ごとにサブエージェント（Read / Grep / Glob のみ、コード変更禁止）を並列起動する。
各エージェントへのプロンプトに以下を必ず含める:

- Phase 0 のユーザーの動機・優先目標・不可侵領域（文脈を運ぶ）
- Phase 1 の兆候のうち当該観点に関わるもの
- **finding の必須フィールド**:
  - (a) 根拠: `file:line` + 実コードの引用（1〜3行）
  - (b) 実害シナリオ: 誰が・いつ・何をすると・何が壊れる/困る
  - (c) 検証方法: 再現手順 or 確認コマンド
  - (d) 修正方針と規模感（S/M/L）
  - (e) 確信度: HIGH（コードで確認済）/ MEDIUM（状況証拠）/ LOW（疑い）
- 「根拠を示せない指摘は本文に載せない。一般論の推奨は『付録: 一般的な改善候補』に隔離」
- 「指摘が0件なら『0件』と明記する。ひねり出さない」

### Phase 4: 反証（adversarial verification）

Phase 3 の全 finding（確信度 LOW を含む）に対して反証パスを実行する:

1. 反証者を1つ選ぶ:
   - デフォルト: 別サブエージェント（general-purpose）に「各 finding を反証せよ。誤読・古い情報・実害のない理論値を疑え」と依頼
   - Codex が使える環境では `codex-second-opinion` スキルでも可（トークンコスト高、Critical 級が多いときに推奨）
2. 判定を三分する:
   - **CONFIRMED**: 反証に耐えた → レポート本文に採用
   - **PLAUSIBLE**: 反証しきれないが確証もない → ラベル付きで残す（要人間確認）
   - **REJECTED**: 誤読・実害なしと判明 → レポートから除外（除外理由は付録に1行残す）

### Phase 5: レポート生成 + 接続提示

`docs/YYYYMMDD_zero_design_report.md` を生成する。**章構成は Phase 2 で選択した観点のみ**。

```markdown
# ゼロベース再設計分析レポート

**プロジェクト**: <name>（種別: <検出結果>）
**分析日**: YYYY-MM-DD
**ユーザーの動機**: <Phase 0 の回答>
**調査観点**: <承認された観点一覧>
**検証**: 全指摘は反証フェーズ通過済み（CONFIRMED N件 / PLAUSIBLE M件 / REJECTED除外 K件）

## エグゼクティブサマリー
3-5行。ユーザーの動機に直接答える形で書く。

## 観点1: <観点名>
### 現状評価
### 良い点（維持すべき設計判断）
### 指摘（優先度順）
各指摘: 根拠 file:line / 実害シナリオ / 検証方法 / 修正方針と規模感 / 確信度 / 反証判定

## 観点2: ...
（同構成。指摘0件の観点は「指摘0件」と明記）

## ゼロから設計するなら
### 技術スタック選定と理由
### 推奨ディレクトリ構造
### 現実的な移行パス（段階的。「全部作り直す」は回答にならない）

## 優先度別アクションアイテム
### 高（即対応すべき）/ 中（次のスプリント）/ 低（余裕があれば）

## 付録
### 一般的な改善候補（根拠 file:line なし。参考情報）
### 反証で除外された指摘（1行ずつ、除外理由付き）
```

評価ルール:
- マーケティング言語禁止（「素晴らしい」「完璧」等は使わない）
- 「なぜ問題か」「何が改善されるか」を必ず明記

**完了報告と次のアクション提示**（自動実行はしない）:

```
✅ zero-design レポート生成完了: docs/YYYYMMDD_zero_design_report.md
   CONFIRMED X件 / PLAUSIBLE Y件（要確認）

次のアクション（推奨順）:
1. /mine-check docs/YYYYMMDD_zero_design_report.md   ← 過去事故との照合（大規模変更前の地雷チェック）
2. /ticket-gen docs/YYYYMMDD_zero_design_report.md   ← チケット分解
```
