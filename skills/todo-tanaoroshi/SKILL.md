# todo-tanaoroshi: 手作業 TODO の棚卸し

manual-todo ハブ（`~/dev/todo/`）に溜まった過去の TODO リストを、**過去記録を証拠に完了判定し、ユーザーと合議して整理する**スキル。目的は2つ：

1. 「終わったか終わってないか分からない TODO」を無くし、ハブを「本当に残っている手作業」だけの見やすい状態に戻す
2. 出した時点ではもっともらしかったが**今見ると妥当でない TODO**（時期尚早・前提が変わった・粒度がおかしい）を見直す

これは一方的な掃除スキルではなく、**一緒に考えるスキル**である。判定に自信がないもの・方針判断が要るものは必ずユーザーに聞く。勝手にチェックをつけたり削除したりしない。

---

## 前提と単位

- **プロジェクト単位で起動する**。証拠（daily_report・git log・docs）はプロジェクト内にあるため、カレントディレクトリのプロジェクトに紐づく TODO だけを扱う
- 対象の特定: `~/dev/todo/state/*.json` の `projectPath` がカレントプロジェクトを指すもの（`registry.json` の `pages` も併読する）
- 引数 `--all` が付いたときのみ全プロジェクト横断モード。ただしプロジェクト外からは証拠が薄いので、判定は保守的にし「そのプロジェクトで /todo-tanaoroshi を起動して」と案内する側に倒す

---

## Phase 1: 収集 — 何が残っているか

1. `~/dev/todo/state/*.json` を読み、対象プロジェクトのリストごとに「未完了タスク一覧（`done: false`）」「最終チェック日時（`checkedAt` の最大値）」「リスト作成日」を整理する
2. 冒頭でスコープ要約を 1 メッセージで提示する：

```
対象: my-app の TODO リスト 3 件
- 2026-08-06 gbp-quota-inngest-key-cleanup: 未完了 9/13（最終チェック 8/07）
- 2026-08-25 local-db-switch-manual-setup: 未完了 8/8（一度も着手なし）
- ...
これから過去記録を調査して完了状況を推定します。
```

未完了がゼロ（全リスト完了済み）なら、Phase 5 の「完了リストの削除確認」だけ行って終了する。

## Phase 2: 証拠調査 — どこを見るか

未完了タスクひとつひとつについて、**実はもう終わっていないか**を過去記録から調べる。見る場所は固定リストではなく、タスクの内容から Claude が選ぶ。典型的な証拠源：

| 証拠源 | 分かること |
|--------|-----------|
| `daily_report/*.md`（タスクより後の日付） | 「〜を設定した」「キーを登録した」等の作業記録 |
| `Plans.md` の引き継ぎ・完了打ち消し | 完了扱いになった項目、方針転換 |
| `git log` / 変更ファイル | `.env.example` 更新・設定ファイル追加など、手作業完了の間接証拠（例: API キー取得タスク → キーを使う実装がコミットされ動作確認済みなら、キーは取得済みのはず） |
| `docs/` のチケット（`- [x]`） | チケット側で完了扱いになっている同内容タスク |
| リポジトリの現物 | DNS 設定タスク → デプロイ済み URL の記載、Social Preview タスク → README の画像、等 |
| `.claude/memory/session-log.md`・セッション履歴 | 該当時期に何をしたか |
| 後続の TODO リスト | 同内容タスクが新リストで再掲され完了している（旧リスト側の消し込み漏れ） |

調査の作法：

- **3 リスト以上を黙って読み進めない**。リストごとに「調査中 → 中間所見」を短く報告しながら進める（沈黙フェーズが長いとユーザーが中断する）
- 証拠は「どのファイルの何を根拠にしたか」を必ず添える。証拠ゼロの推測で「完了」と判定しない
- 間接証拠しかない場合は確信度を下げて Phase 4 で質問に回す

## Phase 3: 判定 — 3分類 + 妥当性

各未完了タスクを次の 3 つに分類する：

1. **完了済みと推定**（証拠あり）→ Phase 4 でチェック承認を求める
2. **未完了・依然有効** → そのまま残す。ただし「いつやるか」「まだブロッカーか」を Phase 4 で確認候補にする
3. **妥当性疑問** → 次のいずれかに該当するもの：
   - **時期尚早**: プロジェクトの現段階に対して先走っている（例: まだ商用レベルに達していないゲームに「Steam 登録」を要求している）。現段階の判定は git log・docs・日報のマイルストーン記述から行う
   - **前提が変わった**: 方針転換・技術変更でタスク自体が無意味になった（例: 使うのをやめたサービスの API キー取得）
   - **粒度・内容がいまいち**: 曖昧すぎる、実は Claude が代行可能、複数タスクが混ざっている

分類 3 は本スキルの核心。manual-todo は生成時点の文脈で「それらしい」タスクを出しがちで、後から見ると段階が合っていないことがよくある。**遠慮なく「これは今やるべきではないと思います」と言う**。ただし判定するのは Claude ではなくユーザー——根拠と推奨を示して委ねる。

## Phase 4: 合議 — ユーザーと決める

リストごと（またはまとめて）に AskUserQuestion で確認する。聞き方の原則：

- **完了済みと推定したもの**: 証拠を添えて「チェックをつけていいですか？」と一括確認（multiSelect で「これとこれは完了扱い」と選ばせる形が扱いやすい）
- **妥当性疑問のもの**: 「前の段階ではこう言っていましたが、現状は〜なので、どうしますか？」と現状認識＋選択肢で聞く。選択肢の例：
  - 削除する（不要になった）
  - 延期する（時期が来たら再掲。Plans.md に「〜になったら manual-todo 再生成」と書き残す）
  - 書き直す（今の段階に合うタスクに作り直す）
  - このまま残す
- **未完了・依然有効なもの**: 数が多い場合のみ「この中で実はもう不要なものはありますか？」と一度だけ確認。基本はそのまま残す
- 慎重側の選択肢（「このまま残す」等）を先頭に置き、誘導しない

## Phase 5: 反映 — state・HTML・ハブ

合議結果を反映する。順序：

1. **チェック反映**: 承認されたタスクの state JSON を `done: true`、`checkedAt` を現在時刻（ISO 8601、`date +%Y-%m-%dT%H:%M:%S%z` で取得）に更新する
2. **タスクの削除・書き直し**: リスト内の一部タスクを削除／変更する場合は、pages の HTML と state JSON の**両方**を整合させて編集する（`data-task-id` と state の `tasks` キーの対応を崩さない）。大幅に作り直す場合は manual-todo スキルの規約に従って新リストとして生成し直し、旧リストは削除する
3. **完了リストの削除**: 全タスク完了になったリストは、ユーザー確認のうえ削除する——pages の HTML・state の JSON を消し、`registry.json` の `pages` から該当 slug を除去する。「アーカイブとして残す」を選んだ場合は削除せず放置でよい（reindex が自動でアーカイブ行に畳む）
4. **reindex**: 変更が 1 件でもあれば `python3 ~/.claude/skills/manual-todo/scripts/todo-hub.py reindex` を実行する
5. **延期の書き残し**: 「延期」と決まったタスクは Plans.md に「（条件）になったら manual-todo で再掲」と 1 行残す。書き残さないと二度と思い出せない

## Phase 6: 完了報告

最後に整理結果を 1 メッセージでまとめる：

```
棚卸し完了:
- チェック消し込み: 5 件（gbp-quota の 4 件、local-db の 1 件）
- リスト削除: 1 件（gemini-api-key-setup、全完了）
- 妥当性見直し: Steam 登録タスクは「M10 到達後に再掲」で延期（Plans.md に記載）
- 残り未完了: 7 件（うち直近やるべきは 〜〜）
ハブ: 進行中 N 件 / アーカイブ M 件
```

「ハブを開いて確認しますか？」と添え、求められたら `todo-hub.py open` で開く。

## アンチパターン

- ❌ 証拠なしに「たぶん終わっている」とチェックをつける（間接証拠のみなら必ず質問に回す）
- ❌ ユーザー確認なしで state 更新・リスト削除を行う
- ❌ 全リストを黙って読み込んでから一括報告する（3 リストごとに中間報告）
- ❌ 妥当性疑問のタスクを Claude の独断で削除する（推奨を示して委ねる）
- ❌ HTML だけ・state だけを片側編集して不整合を作る
- ❌ 延期を決めたのに Plans.md に書き残さない
- ❌ 新しい手作業 TODO の起票までやり始める（それは manual-todo の仕事。必要なら提案だけする）
