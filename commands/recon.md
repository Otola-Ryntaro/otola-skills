# Recon: プロジェクト総ざらい → ゼロから再設計

プロジェクトのコードベースを総ざらいし、「ゼロから自由に再設計できるとしたら？」という
忌憚ない視点で分析・提案・チケット化まで一気に完結させるコマンド。

**核心コンセプト**: 現状の改良ではなく、根本からの再設計を提案する。
美しく完成されたSaaSアプリとして、効率化・セキュリティ・最新の設計思想に基づく理想の構成を示す。

---

## Step 1: スキルのインストール

以下の3スキルをプロジェクトにインストールする：

```bash
npx skills add outfitter-dev/agents@codebase-recon -y
npx skills add openhands/skills@codereview-roasted -y
npx skills add aj-geddes/claude-code-bmad-skills@system-architect -y
```

## Step 2: 成果物フォルダの準備

現在時刻を取得し、以下のフォルダを作成する（存在しない場合は先に `docs/` も作成）：

- `docs/(Y_M_D)_report/` — 分析レポート3本を格納
- `docs/tickets_(Y_M_D)/` — 作業チケット群を格納

例：`docs/2026_3_1_report/`、`docs/tickets_2026_3_1/`

---

## Step 3: Phase 1 — コードベース偵察

codebase-recon スキルを使い、プロジェクト全体を体系的に偵察する。

### 調査対象（漏れなく把握する）

- ディレクトリ構造・ファイル構成の全体像
- 使用技術スタック・フレームワーク・ライブラリ・バージョン
- 依存関係グラフ（内部モジュール間・外部パッケージ）
- データベース構造・スキーマ設計
- 認証・認可の仕組み
- API設計・エンドポイント構成
- デプロイ・CI/CDパイプライン
- テスト構成・カバレッジ状況
- 設定管理・環境変数の扱い

### 出力

`docs/(Y_M_D)_report/phase1_recon.md` に現状マップとして保存する。

---

## Step 4: Phase 2 — 忌憚ない意見（Roasted Review）

`docs/(Y_M_D)_report/phase1_recon.md` を Read した上で、codereview-roasted スキルを使う。

### Phase 1 からの引き継ぎ指示

Phase 1 レポートで把握したコードベースの全体像を踏まえ、以下の観点で容赦なく指摘する：

- **褒め言葉は一切禁止。改善案より先に問題点の摘出を優先する。**
- SaaSアプリとして根本的に欠けているもの・古いもの・危ないものを全て列挙
- 技術的負債・アーキテクチャの欠陥・設計上の矛盾
- セキュリティ上のリスク・脆弱な部分
- スケーラビリティ・保守性の問題
- 現代のSaaSベストプラクティスとのギャップ
- コードの品質・一貫性・テスト不足の問題

**重要**: 「もし今ゼロから設計するとしたら、絶対にこの設計にはしない」という判断基準で批評する。

### 出力

`docs/(Y_M_D)_report/phase2_opinion.md` に問題点一覧として保存する。

---

## Step 5: Phase 3 — ゼロから再設計（BMAD Reconstruction）

`docs/(Y_M_D)_report/phase1_recon.md` と `docs/(Y_M_D)_report/phase2_opinion.md` を
両方 Read した上で、system-architect スキルを使う。

### Phase 1 + 2 からの引き継ぎ指示

現状の技術スタック・問題点・欠陥を完全に把握した上で、
BMADフレームワーク（Business / Model / API / Data）に沿ってゼロから設計する：

**重要な姿勢**:
- 現状実装への縛りは一切なし。白紙に戻す前提で考える
- 「今の実装を直す」ではなく「理想のSaaSとして最初から作るなら」という視点
- Phase 2 で明らかになった問題点を根本から解決する設計にする

**設計の観点（BMADフレームワーク）**:

```
Business（ビジネス要件・目的・スケーラビリティ戦略）
    ↓
Model（ドメインモデル・データモデル・エンティティ設計）
    ↓
API（エンドポイント設計・インターフェース・認証方式）
    ↓
Data（ストレージ選定・データフロー・キャッシング戦略）
```

**必ず含める内容**:
- 推奨技術スタックとその選定理由
- アーキテクチャパターン（モノリス/マイクロサービス/モジュラーモノリス等）
- セキュリティ設計（認証・認可・データ保護）
- インフラ・デプロイ戦略
- 観測可能性（ロギング・モニタリング・アラート）
- 開発体験の向上策（CI/CD・テスト戦略）
- 移行コスト・リスクの考慮（現状からの移行パス概要）

### 出力

`docs/(Y_M_D)_report/phase3_reconstruction.md` に再設計提案として保存する。

---

## Step 6: 作業チケットの生成

3本のレポート（`phase1_recon.md`、`phase2_opinion.md`、`phase3_reconstruction.md`）を
すべて Read した上で、実際の作業に細分化したチケットを生成する。

### チケット設計の方針

- Phase 3 の再設計提案を実行可能な作業単位に分解する
- 各チケットに「優先度（High/Medium/Low）」「前提チケット（依存関係）」「概算規模（S/M/L/XL）」を明記
- 現状からの移行を考慮した段階的な実施順序にする

### 生成するチケットファイル

`docs/tickets_(Y_M_D)/` 配下に以下を作成する：

| ファイル | 内容 |
|---------|------|
| `00_overview.md` | 全体サマリー・優先順位マップ・実施ロードマップ |
| `01_foundation.md` | 基盤・インフラ・フレームワーク・アーキテクチャ変更 |
| `02_data_model.md` | DB設計・データモデル・スキーマ刷新 |
| `03_api.md` | APIエンドポイント設計・認証・認可の再構築 |
| `04_frontend.md` | UI/UX・フロントエンドアーキテクチャ再設計 |
| `05_security.md` | セキュリティ対応・脆弱性修正・セキュリティ設計 |
| `06_devops.md` | CI/CD・デプロイパイプライン・監視・観測可能性 |

各チケットファイルのフォーマット：
```markdown
# [カテゴリ名] 作業チケット

## 概要
（このカテゴリで何をするかの全体像）

## チケット一覧

### TICKET-XXX: [作業タイトル]
- **優先度**: High / Medium / Low
- **規模**: S / M / L / XL
- **依存**: TICKET-YYY（なければ「なし」）
- **内容**: 具体的な作業内容の説明
- **完了条件**: 何ができたら終わりか
```

---

## Step 7: 後片付けコマンドの表示（省略禁止・必須）

**この Step 7 は、全ての作業が終わった後に必ず実行すること。省略・スキップ厳禁。**

以下のメッセージをそのままユーザーに表示する：

---

✅ recon 完了。以下のファイルが生成されました：

- `docs/(Y_M_D)_report/phase1_recon.md` — 現状マップ
- `docs/(Y_M_D)_report/phase2_opinion.md` — 忌憚ない問題点一覧
- `docs/(Y_M_D)_report/phase3_reconstruction.md` — ゼロから再設計提案
- `docs/tickets_(Y_M_D)/` — 作業チケット群（7ファイル）

**スキルを削除するには、以下をターミナルでコピペ実行してください：**

```bash
rm -rf .agents/skills/codebase-recon
rm -rf .agents/skills/codereview-roasted
rm -rf .agents/skills/system-architect
```
