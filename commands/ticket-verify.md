# Ticket Verify: 実装検証（並列サブエージェント）

全チケット完了後、元レポートの提案が漏れなく実装されているかを
**サブエージェント並列実行**で検証し、検証レポートを生成する。

> ticket-gen の Phase 7 を独立コマンド化したもの。
> 単独実行可、`/next` から全 Phase 完了時に推奨される。

## 引数

```
/ticket-verify <tickets-dir>                       → デフォルト（3 subagent 並列）
/ticket-verify <tickets-dir> --report <レポート>   → 元レポートを明示指定
/ticket-verify <tickets-dir> --lite                → 軽量版（Agent A のみ）
/ticket-verify <tickets-dir> --skip-todo-check     → 未完了チケットがあっても実行
```

`<tickets-dir>` の例: `docs/tickets20260321/` または `docs/tickets20260321/ticket_index.md`

---

## Step 0: 検証準備

1. 引数から tickets ディレクトリ（または ticket_index.md）パスを取得（必須）
2. `ticket_index.md` を Read し、**全チケットが ✅ 完了** であることを確認
   - 未完了チケットがある場合は停止し、未完了チケット一覧を表示してユーザー判断を仰ぐ
   - `--skip-todo-check` 指定時は警告を出して続行
3. **元レポート**を特定:
   - `--report` 指定時: そのパスを使用
   - 未指定時: ticket_index.md の冒頭・「元レポート」セクション・「検証コマンド」セクションから取得
   - 見つからない場合はエラー終了（パス指定を促す）
4. 元レポートを Read し、**検証対象リスト**を抽出:
   - レポート内の「提案」「対策」「施策」「改善項目」を列挙
   - 各項目の期待される成果（ファイル変更、動作変更、数値改善）を特定
   - 「除外項目」「優先度を上げなくていい」と明記された項目は検証対象外とマーク

---

## Step 1: 並列サブエージェント実行

以下の 3 つの検証を **Agent ツールで並列起動** する（`--lite` 時は Agent A のみ）。

### Agent A: コード整合性チェック

- **subagent_type**: `general-purpose`（レビュー観点は下記チェック項目をプロンプトで指示する）
- **タスク**: 各チケットの「変更対象ファイル」を読み取り、レポートの提案通りに実装されているか確認
- **チェック項目**:
  - チケットの受け入れ条件（`- [x]`）が実際のコードと一致するか
  - 型エラー・未使用 import・デッドコードがないか
  - 新規追加コードが既存パターンに従っているか
- **出力形式**: `{ file, status: 'ok' | 'issue', detail }[]`

### Agent B: テスト・ビルド検証

- **subagent_type**: `general-purpose`（検証コマンドの実行と結果解析をプロンプトで指示する）
- **タスク**: `npm run typecheck` と関連テストファイルの実行
- **チェック項目**:
  - TypeScript コンパイルエラーがないか
  - 変更ファイルに対応するテストが全て pass するか
  - テストカバレッジが著しく低下していないか
- **出力形式**: `{ check, passed: boolean, detail }[]`

### Agent C: レポート突合せ（Gap 分析）

- **subagent_type**: `Explore`
- **タスク**: 元レポートの提案リストと実際の git diff（レポート作成日以降のコミット）を突合せ
- **チェック項目**:
  - レポートに記載されているが未実装の項目（false negative）
  - レポートに記載されていないが実装された項目（scope creep）
  - 「除外項目」が誤って実装されていないか
- **出力形式**: `{ item, reportSection, status: 'implemented' | 'missing' | 'excluded' | 'extra', detail }[]`

---

## Step 2: 結果統合 + レポート生成

サブエージェントの結果を統合し、以下のフォーマットで `codex/{YYYYMMDD}_{tickets-dir名}_verification_report.md` を生成する。
`{YYYYMMDD}` は実行日（`date +%Y%m%d`）、`{tickets-dir名}` は対象ディレクトリ名（例: `tickets20260321_refactor`）。
Wave 名をファイル名に含めることで、同日に複数 Wave を検証しても帰属が混線しない。

レポート生成後、**ticket_index.md の「## 実行記録」セクション**（無ければ作成）に以下を 1 行追記する。
`/next` Step 5-0 がこの記録を一次ソースとして検証済み判定を行う:

```markdown
- 実装検証: ✅ YYYY-MM-DD / 判定: 合格（または ⚠️ 指摘 N 件） / レポート: codex/{YYYYMMDD}_{tickets-dir名}_verification_report.md
```

```markdown
# 実装検証レポート

**元レポート**: `<元レポートパス>`
**チケットシリーズ**: {PREFIX}-001〜{PREFIX}-NNN
**検証日**: YYYY-MM-DD
**検証結果**: ✅ 全項目合格 / ⚠️ N件の指摘あり / ❌ N件の未実装あり

## 1. コード整合性

| ファイル     | ステータス | 詳細             |
| ------------ | ---------- | ---------------- |
| lib/xxx.ts   | ✅ OK      | チケット通り     |
| hooks/yyy.ts | ⚠️ 指摘    | 未使用importあり |

## 2. テスト・ビルド

| チェック          | 結果    | 詳細       |
| ----------------- | ------- | ---------- |
| TypeScript        | ✅ Pass | エラーなし |
| テスト (N suites) | ✅ Pass | 全 pass    |

## 3. Gap 分析（レポート突合せ）

### 実装済み項目

| #   | レポート記載       | 実装チケット | ステータス  |
| --- | ------------------ | ------------ | ----------- |
| 1   | review-only prompt | GEN-001      | ✅ 実装済み |

### 未実装項目（要対応）

| #   | レポート記載         | 理由 | 推奨アクション |
| --- | -------------------- | ---- | -------------- |
| -   | （なければ「なし」） |      |                |

### 除外項目（対応不要）

| #   | レポート記載          | 除外理由     |
| --- | --------------------- | ------------ |
| 1   | latency-aware routing | 事業判断次第 |

### スコープ外の追加実装

| #   | 実装内容             | 理由 |
| --- | -------------------- | ---- |
| -   | （なければ「なし」） |      |

## 4. 総合判定

- **合格条件**: 未実装項目が0件 かつ Critical指摘が0件
- **判定**: ✅ 合格 / ❌ 不合格（要修正 N 件）
- **次のアクション**: （不合格時のみ記載）
```

---

## Step 3: 不合格時の対応

- **Critical 指摘**: 即座にユーザーに報告し、修正チケットを提案
- **Minor 指摘**: レポートに記載し、ユーザー判断に委ねる
- **未実装項目**: 追加チケットとして ticket_index.md に Phase N+1 を追加提案

```markdown
## 追加チケット提案

未実装項目を以下のチケットとして追加することを提案します:

- {PREFIX}-XXX: 〇〇を実装（推定: M）
- {PREFIX}-YYY: 〇〇のテスト追加（推定: S）

ticket_index.md に Phase N+1 として追加しますか？（yes/no）
```

---

## Step 4: 完了報告

```
## /ticket-verify 完了

**対象**: <tickets-dir>
**元レポート**: <元レポートパス>
**検証結果**: ✅ 全項目合格 / ⚠️ N件の指摘あり

### 検証レポート
- `codex/{YYYYMMDD}_{tickets-dir名}_verification_report.md`
- ticket_index.md の「実行記録」に追記済み

### サマリ
- コード整合性: N件OK / N件指摘
- テスト・ビルド: ✅ Pass / ❌ N件失敗
- Gap 分析: N件実装済み / N件未実装 / N件除外 / N件スコープ外

### 次のアクション
- 合格時: `/next` でリリース提案へ
- 不合格時: 追加チケット作成 → `/ko` で再着手
```

---

## エラー処理

- **tickets ディレクトリが見つからない**: 引数誤りとしてエラー終了
- **未完了チケットがある**: 一覧表示して停止（`--skip-todo-check` で続行可）
- **元レポートが見つからない**: `--report <パス>` を促してエラー終了
- **subagent 実行失敗**: 失敗した Agent のセクションは「実行失敗」と記録し、他は続行

---

## 関連コマンド

- `/ticket-gen <レポート>` — チケット生成（前段）
- `/ticket-review <tickets-dir>` — 計画品質レビュー
- `/ko <ticket_index.md> Phase N` — 各 Phase 実装
- `/next` — Phase 進捗管理（全完了時に本コマンドを推奨）
