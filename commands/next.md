# Next: Phase単位の進捗管理 → 次の作業提示

ticket_index.md のPhase構成を読み取り、Phase単位で進捗を判定し、
次に取り組むべきPhaseとその中のチケットを提示する。

---

## Step 0: 未コミット変更のコミット（スコープ限定）

1. `git status` で未コミット変更を確認する
2. **変更がある場合**:
   - `git diff` と `git diff --staged` で変更内容を把握する
   - **ステージング対象を直前の作業に限定する**: 会話コンテキスト・チケットの「対象ファイル」から、直前の作業に関連する変更ファイルのみを判定して個別にステージする（`git add -A` / `git add .` の一括ステージは禁止）
   - **無関係な変更は巻き込まない**: 関連と判定できないファイルは一覧をユーザーに提示し、未ステージのまま残す
   - `git log --oneline -5` でコミットメッセージのスタイルを確認する
   - 変更内容に応じた適切なコミットメッセージを作成する
   - コミットを実行する（Co-Authored-By 付き）
3. **変更がない場合**: そのまま Step 1 へ進む

> **注意**: `.env*` やシークレットを含むファイルはステージングしない。
> **注意**: Step 3 でチケットファイル・ticket_index.md の進捗マークを更新した場合は、同じコミットに同梱するか追加コミットする（進捗マークだけが次回コミットに漏れる状態を作らない）。

---

## Step 1: ticket_index.md の特定

`$ARGUMENTS` でパスが指定されていればそれを使用。未指定の場合は以下のパターンで探索する（優先度順）:

1. `docs/ticketsYYYYMMDD*/ticket_index.md` — 日付付きフォルダ（最新日付を優先）
2. `codex/ticketsYYYYMMDD*/ticket_index.md` — codex配下
3. `docs/Ticket_index.md` — レガシー形式（フォールバック）

**複数存在する場合**: **未完了チケットを持つ Wave が複数あるときは、必ず全 Wave の一覧（残チケット数付き）を提示し、対象をユーザーに確認する**。最新日付を黙って選ばない（旧 Wave の残チケットが誰にも提示されず孤児化するのを防ぐ）。未完了 Wave が1つだけならそれを対象とする。

---

## Step 2: Phase進捗の判定

ticket_index.md を Read し、「Phase 構成」テーブルと「チケット一覧」テーブルを解析する。

### 判定ロジック

各Phaseについて、所属チケットのステータスを集計:
- **Phase完了**: Phase内の全チケットが ✅
- **Phase進行中**: Phase内に 🔄 または一部 ✅ がある
- **Phase未着手**: Phase内の全チケットが ⬜
- **Phase着手可能**: 依存する前Phaseが全て完了済み、かつ自身は未着手

### アクティブPhaseの決定

1. 🔄 進行中のPhaseがあればそれがアクティブ
2. なければ、最初の着手可能な未着手Phaseがアクティブ
3. 全Phase完了なら「全完了」を報告

---

## Step 3: 状態の突合（reconciler）

**進捗マーク（🔄/✅）の writer は /ko である。** /next はマークを新規に書くのではなく、状態の整合を検証し、ズレがあれば証拠に基づいて修復を**提案**する。

1. **三点突合**: 各チケットについて以下の3箇所を照合する:
   - チケットファイル内の checkbox（作業内容・受け入れ条件）
   - ticket_index.md のチケット一覧ステータス
   - ticket_index.md の Phase 構成テーブルのステータス
2. **完了主張の証拠確認**（ファイル記録が一次ソース、会話コンテキスト・git log はフォールバック）:
   - **Strict チケット**: チケットファイル末尾の「レビュー記録」（`/cr --spec` が追記）で spec 充足を確認。記録が無ければ会話 / git log を確認し、それでも無ければ警告 `⚠️ {ticket-id}: spec compliance check の記録がありません。/cr --spec {ticket-path} で確認することを推奨` → ユーザーに続行可否を確認。spec gap が残る場合は完了扱いを保留
   - **非 strict チケット**: テスト / ビルド / lint の実行記録（レビュー記録 → 会話 → git log の順）を確認。無ければ `⚠️ {ticket-id}: 検証実行の記録が見つかりません` と警告してユーザーに確認する（推測だけで完了扱いしない）
3. **ズレの修復提案**（無断修復しない）:
   - 例: チケットの checkbox 全完了 + レビュー記録あり、なのに index が ⬜/🔄 → 「✅ に更新」を提案して承認後に修復
   - 証拠が無いズレは修復せず、内容を提示してユーザーに判断を仰ぐ
4. **中断異常の検出**: 🔄 のチケットに「未コミット差分もレビュー記録もない」場合、中断異常として報告し、再着手（/ko）か ⬜ への差し戻し（理由1行を添える）をユーザーに確認する
5. 判断がつかない場合はユーザーに1つだけ質問する

---

## Step 3.5: 発見事項（途中発覚）の処理

ticket_index.md の「発見事項（途中発覚）」セクションに**状態: 未処理**の項目がある場合、項目ごとに以下の選択肢を提示して処理する:

1. **チケット追加**: 既存最大番号 +1 で採番（/ticket-review Step E と同じ規則）し、チケットファイル生成 + index の Phase 表・一覧を更新
2. **既存 Phase に挿入 / 新 Phase 追加**: 依存関係に応じて配置
3. **✅ の取り消し（差し戻し）**: 発見事項が完了済みチケットの前提を崩す場合、該当チケットを ⬜ に戻し、理由を1行添える
4. **却下**: 対応不要と判断。理由1行を「状態」列に記録

処理した項目は「状態」列を更新する（未処理 → チケット化済（ID）/ 却下）。発見事項が無ければこの Step はスキップ。

## Step 5: 全Phase完了時のリリース提案

全Phaseが完了（未着手チケット0件）の場合、以下のリリース提案を行う。

### 5-0. 実装検証（ticket-verify）の実行推奨

リリース提案の前に、まだ `/ticket-verify` が未実行の場合は推奨する:

```
全 Phase が完了しました。リリース前に実装検証を実行することを推奨します:
  /ticket-verify docs/tickets{YYYYMMDD}/

検証済み、またはスキップする場合は `/next --skip-verify` で続行してください。
```

実行済みかは **ticket_index.md の「実行記録」セクション**（/ticket-verify が完了時に追記する）で判定する。
記録が無い場合のフォールバックとして `codex/*_{tickets-dir名}_verification_report.md` の存在を確認する（Wave 名を含むファイルのみ。日付だけの一致で判定しない — 同日の別 Wave と誤認するため）。

- **実行記録（またはレポート）あり** または `--skip-verify` 指定時: Step 5-1 へ進む
- **記録なし** かつ `--skip-verify` なし: 上記推奨を表示してユーザー判断を仰ぐ

### 5-1. バンプ種別の自動判定

最新のバージョンタグ（`v*`）から現在の HEAD までのコミットメッセージを解析し、バンプ種別を判定する:

```bash
# 最新タグを取得
LAST_TAG=$(git tag --sort=-v:refname | grep -E '^v[0-9]' | head -1)

# コミットメッセージを解析
git log --format='%s' ${LAST_TAG}..HEAD
```

**判定ルール**:
- `BREAKING` または `!:` を含むコミット → **major**
- `feat(` または `feat:` で始まるコミット → **minor**
- それ以外（`fix:`, `refactor:`, `docs:` 等のみ） → **patch**

### 5-2. リリース提案の出力

バンプ種別を判定したら、**バージョンバンプ → コミット → タグ → push を一括で実行するコマンド**を提案する。
ユーザーが「やって」と言えばそのまま実行できる形にする。

```
## 🚀 リリース提案

全チケット完了。リリース準備が整っています。

### バンプ種別: minor（自動判定）

**判定根拠**（v1.0.0..HEAD）:
- feat(VER-006): /help ヘルプサイト基盤
- feat(VER-007~010): /help コンテンツページ群
- feat(VER-011): サイドバー・ログイン画面にヘルプリンク追加

### 実行コマンド（コピペ可）

npm version minor -m "release: v%s" && git push origin main --tags

### 内訳
1. `npm version minor` → package.json を 1.0.0 → 1.1.0 に更新、コミット + タグ `v1.1.0` を自動作成
2. `git push origin main --tags` → コミットとタグをリモートにプッシュ → Vercel 自動デプロイ

💡 「やって」で上記を実行します。patch/major の場合は `npm version patch` / `npm version major` に読み替え。
```

**重要**: `npm run release` スクリプトが存在する場合はそちらを優先提案する。
存在しない場合は `npm version {bump} && git push` を提案する。
いずれの場合も、**push コマンドまで含めた一括実行可能な形で提示する**こと。

### 5-3. リリース不要の判定

以下の場合はリリース提案をスキップする:
- 全チケットが `docs:` のみのコミットで構成される場合
- ticket_index.md のタイトルに「調査」「分析」「レポート」等の非実装ワードが含まれる場合

その場合は「リリース不要（ドキュメント/調査のみ）」と報告する。

---

## フォールバック

Phase構成テーブルがない ticket_index.md の場合は、チケット一覧から優先度ベースで提示する:

- **High**: 他チケットが依存 / セキュリティ / 基盤系
- **Medium**: High 完了後に着手できる / 機能実装系
- **Low**: 単独完結 / ドキュメント / DevOps系

---

## 注意事項

- ticket_index.md 自体はチケットとして扱わない（管理ファイル）
- レポートファイル（`phase1_recon.md` 等）もチケットとして扱わない
- チケットかどうかは `- [ ]` / `- [x]` の存在で判断する
