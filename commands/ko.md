# Task Kickoff（Phase対応）

作業を開始します。

## タスク

$ARGUMENTS

## 実行手順

### 0. 入力の解析

引数を解析して実行モードを判定する:

- **Phase指定モード**: `<ticket_index.mdパス> Phase N` → Phase単位で実行
  - 例: `/ko docs/tickets20260321/ticket_index.md Phase 2`
- **直接タスクモード**: 上記以外 → 自由記述のタスクを実行

Phase指定モードの場合は Step 0-1 へ。直接タスクモードの場合は Step 1 へ。

### 0-1. Phase指定モード: チケット特定

1. 指定された ticket_index.md を Read する
2. Phase構成テーブルから対象Phaseのチケット一覧を取得する
3. 各チケットファイルを Read して「作業内容」「受け入れ条件」「元レポート該当箇所」セクションを把握する
4. 前提Phaseが完了済みであることを確認する（未完了なら警告してユーザーに確認）
5. **着手前調査（必須）**: 実装に入る前に、チケットごとに以下を確認する。数分の recon が誤実装のやり直しより安い:
   - チケットの「対象ファイル」を Read し、現状の実装・既存パターン（命名・エラー処理・import スタイル）を把握する
   - 変更範囲に関連するテストファイルを特定する（なければ「テストなし」と認識しておく）
   - プロジェクトの CLAUDE.md の禁忌・Never 系セクションに抵触しないか確認する
   - チケットの想定と実コードが食い違う場合（ファイルが無い、既に修正済み等）は、実装せず ticket_index.md の「発見事項（途中発覚）」セクションに1行追記（セクションが無ければ作成）したうえでユーザーに報告する（会話にしか残らない状態を作らない）

### 0-2. Strict モード判定（Phase指定モード時）

各チケットについて、以下のいずれかに該当する場合 **strict モードを自動発動** する。
strict モード対象チケットがあれば、その旨をユーザーに報告してから着手する。

**自動発動条件**:

- チケットファイルに `🔒` マーカーがある（DB/migration 系、既存 MIGRATION-CHECK 連携）
- チケットの優先度が `HIGH`
- チケット本文・対象ファイル・受け入れ条件のいずれかに以下のキーワードが含まれる（大文字小文字無視）:
  - 認証・決済系: `auth`, `clerk`, `supabase auth`, `stripe`, `payment`, `subscription`, `webhook`
  - シークレット・トークン系: `secret`, `token`, `api key`, `webhook secret`
  - データ層: `migration`, `prisma`, `supabase db`, `rls`, `policy`, `schema`

**明示フラグ**:

- `--strict`: 全チケットに対して strict モードを強制発動
- `--no-strict`: 自動発動を抑制（軽微な変更で品質コストを払いたくない場合）
- `--fresh`: `superpowers:subagent-driven-development` に完全委譲（重い品質モード、オプトイン）
  - implementer + spec-reviewer + code-quality-reviewer の3 subagent を per-task で dispatch
  - 超重要チケット用、token コストが大きい

判断に迷ったら **付ける側に倒す**（false positive の方が false negative より害が少ない）。

**追加チェック（strict 判定の報告時に実施）**:

- **🔒 Wave の計画レビュー未実行警告**: Phase に 🔒 または HIGH チケットが含まれるのに、ticket_index.md の「実行記録」に計画レビューの記録がない場合、`⚠️ 計画レビュー未実行の 🔒 Wave です。/ticket-review <tickets-dir> の実行を推奨します` と警告して続行可否を確認する（自動実行はしない）
- **ブランチ提案（🔒/HIGH を含む Wave の初回 /ko 時のみ、任意）**: フィーチャーブランチの作成を1行提案する。ユーザーが不要と言えば main のまま進めてよい（push は /ticket-verify 合格後のリリース時のみ、という push ゲート型運用が前提）

### 0-3. 着手マーク（Phase指定モード時・必須）

実装開始の直前に ticket_index.md を更新する:

1. Phase 構成テーブルの対象 Phase のステータスを 🔄 に更新
2. チケット一覧の着手チケットのステータスを 🔄 に更新

**進捗マーク（🔄/✅）の writer は /ko のみ**。/next は突合・修復提案のみ行う（書き手を一本化してズレを防ぐ）。
中断してもこの 🔄 が「作業中だった」証拠として残り、/next が中断異常を検出できる。

### 1. タスクの分解

TodoWrite でタスクをサブタスクに分解する。各サブタスクは独立して完結できる単位にする。

**Phase指定モードの場合**: 各チケットの「作業内容」のチェックボックスをサブタスクとして取り込む。

**Strict モード時の追加**: 「受け入れ条件」セクションのチェックボックス項目も **1条件 = 1 todo** として TodoWrite に個別登録する。実装中に視覚的に進捗追跡することで抜け漏れを防ぐ。

### 2. 並列実行の判断

- **Phase構成で「全て並列」**: サブエージェントで全チケットを並列実行する（下記の委譲プロトコルに従う）
- **Phase構成で「単独」**: 順次実行する
- **直接タスクモード**: サブタスク間の依存関係で判断する

#### 2-1. 並列委譲プロトコル（サブエージェント使用時は必須）

サブエージェントへの委譲は「チケットパスを渡すだけ」を禁止し、以下を守る。実装意図がサブエージェントまで届かないことが品質劣化の最大要因。

**渡すもの（プロンプトに必ず含める）**:

1. チケット本文の全文（「背景」「作業内容」「受け入れ条件」「元レポート該当箇所」「対象ファイル」を含む）
2. プロジェクト CLAUDE.md の禁忌・Never 系セクションと、チケットに関連するルール
3. strict モード対象の場合はその旨と、受け入れ条件を1件ずつ充足確認する義務
4. 「対象ファイル以外への変更は原則禁止。必要になったら変更せず報告する」という Surgical Changes 指示

**返させるもの（報告フォーマットを指定する）**:

1. 変更ファイル一覧（ファイルごとに変更概要1行）
2. 受け入れ条件ごとの充足状況（✅ / ❌ + 根拠）
3. 実行した検証コマンドとその結果（テスト・lint・typecheck。実行していなければ「未実行」と明記させる）
4. チケット想定との食い違い・スコープ外で気付いた問題（あれば）

**メイン側の責務**: 各サブエージェントの報告を受けたら、受け入れ条件の充足と検証コマンドの結果をメイン側で再確認してから Step 3（レビュー）に進む。strict チケットの self-review + spec check はサブエージェント側で実施させたうえで、メイン側でも `/cr --spec` を再実行する（二重ゲート）。サブエージェントが報告した「チケット想定との食い違い・スコープ外の問題」は ticket_index.md の「発見事項（途中発覚）」に1行追記する。

### 3. 実装 → コードレビューのサイクル

各サブタスクの実装が完了したら、以下の優先順位でコードレビューを実施する：

#### 3-strict. Strict モード時の追加レビュー（通常レビューの前）

strict モード対象のチケットでは、通常のコードレビュー（下記の優先順位）に入る前に
以下を **必ず** 実行する。superpowers の subagent-driven-development が持つ
「self-review + spec compliance review」の本質を取り込んだ軽量実装。

1. **Self-review**: 直前の diff を Claude 自身で観点別に確認:
   - **Completeness**: 受け入れ条件を全て満たしたか（`-strict` で TodoWrite に展開した条件と照合）
   - **Quality**: 命名・可読性・YAGNI 違反なし
   - **Discipline**: 既存パターン遵守、過剰実装なし、Surgical Changes（無関係箇所を触っていない）
   - **Testing**: テストが実装に追従しているか
2. **Spec compliance check**: `/cr --spec <チケットパス>` を **自動呼び出し** する
   - チケットの受け入れ条件 vs 実際の git diff を照合
   - missing / extra / misunderstanding を検出
   - Critical（spec gap）が出たら修正→再 spec check のループ（Critical=0 まで）
3. その後、通常モードのレビュー（`/cr`）に進む

`--fresh` モード時は上記 1-3 を全て `superpowers:subagent-driven-development` に委譲する
（implementer + spec-reviewer + code-quality-reviewer を per-task で fresh dispatch）。

#### 通常モードのレビュー

通常モードでは `/cr` を実行する（strict モードは 3-strict の通り `/cr --spec <チケットパス>`）。

**レビュー手段の選択・優先順位（harness / subagent / Codex 等）は cr.md が唯一の持ち主**であり、本ファイルには重複して持たせない。手段を明示したい場合は `/cr --codex` `/cr --adversarial` 等のフラグで指定する。

### 4. レビュー指摘の対応

コードレビューで指摘された問題を修正してから次のサブタスクに進む。
軽微な指摘はまとめて対応しても良いが、重大な問題は即時修正する。

**バグ系指摘は症状パッチ禁止**: 再現 → 根本原因特定 → 根本原因側の修正 → 回帰テスト、の順で対応する（/cr Phase 1.7 の Root-Cause 分析と同じ型）。症状箇所だけを塞ぐ修正（null チェック追加だけで混入源を放置する等）は修正完了と見なさない。再現可能なバグは `superpowers:systematic-debugging` の利用を推奨。

### 5. 完了確認

全サブタスク完了後:

0. **実行検証ゲート（完了マーク前に必須）**:
   - プロジェクトの検証コマンドを検出する（package.json の scripts / CLAUDE.md の記載 / Makefile 等）
   - 最低限 **typecheck / lint + 変更範囲に関連するテスト** を実際に実行する（「作業内容のチェックを付けた」だけでは通過しない）
   - strict モード時は **build まで** 実行する
   - 失敗が残る状態での完了マークは禁止。修正して再実行、または失敗内容をユーザーに報告して判断を仰ぐ
   - 検証コマンドが存在しないプロジェクトでは「検証コマンドなし」と報告に明記する
1. TodoWrite で完了状態を確認する
2. **Strict モードの場合（完了マーク前の検証）**:
   - spec compliance check の結果を確認: Critical（spec gap）が残っていれば完了マーク禁止
   - 受け入れ条件 todo（Step 1 で展開したもの）が全て完了しているか確認
   - 不充足があればユーザーに警告し、追加修正の判断を仰ぐ
3. **Phase指定モードの場合**:
   - 各チケットファイルのチェックボックスを `[x]` に更新する
   - ticket_index.md のチケット一覧ステータスを ✅ に更新する
   - Phase内の全チケットが完了した場合、Phase構成テーブルのステータスも ✅ に更新する
4. タスク全体の完了を報告する
5. `/next` の実行を提案する

---

## 使い方

```
/ko <タスク内容>                              → 直接タスクモード
/ko <ticket_index.mdパス> Phase N             → Phase指定モード（strict 自動判定）
/ko <ticket_index.mdパス> Phase N --strict    → 強制 strict
/ko <ticket_index.mdパス> Phase N --no-strict → 自動発動を抑制
/ko <ticket_index.mdパス> Phase N --fresh     → superpowers:subagent-driven-development に委譲
```
